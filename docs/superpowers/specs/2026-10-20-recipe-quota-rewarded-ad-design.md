# 레시피 생성 제한 + 보상형 광고 설계

- 작성일: 2026-10-20
- 상태: 운영자 결정 반영, 최종 승인 대기
- 관련: 스위치온 패스 (`docs/superpowers/specs/2026-10-19-switchon-pass-payment-design.md`). 패스 보유 여부로 한도가 달라진다.

## 1. 배경과 목적

레시피 1개를 만들 때마다 이미지 생성 비용(`gemini-3.1-flash-image`, 장당 약 90원)이 든다. 지금은 생성 횟수에 제한이 없다.

최근 2주(2026-10-06~20) 실제 사용량:
- 레시피 68개 (모두 이미지 포함), 하루 평균 약 5개 → 월 약 1만 4천 원
- 유저 37명. 유저·날 기준 하루 1개 65%, 2개 26%, 3개 7%, 5개 2% (최대 5개)

운영자 목표: **비용 안전장치** (운영자 결정). 패스 구매 유도는 부차적이다. 평소 쓰는 유저는 거의 걸리지 않아야 한다.

## 2. 목표 / 비목표 / 안티 목표

### 목표
- 유저별 하루 레시피 생성 수 제한 (KST 자정 기준)
- 무료 한도를 다 쓴 무료 유저는 **보상형 광고를 끝까지 보면 1개 더** 만들 수 있음 (운영자 결정)
- 한도·광고 보너스 수치는 DB 설정으로 앱 업데이트 없이 변경

### 비목표
- 배너·전면 광고 등 다른 광고 형태
- 레시피 외 다른 기능의 사용량 제한
- 광고 수익 극대화

### 안티 목표
1. 생성이 실패했는데 횟수만 차감됨
2. 광고를 끝까지 봤는데 보너스를 못 받음
3. 앱 조작으로 한도를 넘거나 가짜 광고 보상을 받음 (비용 안전장치가 무의미해짐)
4. 패스 보유자에게 광고가 보임

## 3. 결정된 내용

### 3.1 한도 (제안을 운영자가 승인 — 2026-10-20 "비용 안전장치")

| 유저 | 하루 기본 한도 | 광고 보너스 |
|---|---|---|
| 무료 | 5개 | 광고 1회당 +1, 하루 최대 3회 |
| 패스 구매자 (`user_pass.pass_expires_at > now()`) | 20개 | 없음 (광고 안 보임) |

- 무료 5개: 지난 2주 최대치. 현재 유저는 걸리지 않는다.
- 패스 20개: 무제한이면 안전장치가 아니므로 상한만 높게 둔다 (내 결정).
- 하루 경계는 KST 자정.
- **패스 결제의 무료 기간은 레시피 한도와 무관하다.** 무료 기간에는 구독 전용 기능만 모두에게 열리고, 레시피는 무료 한도(5개 + 광고 보너스)를 그대로 쓴다. 무료 기간이 시작될 때 모든 유저의 한도가 20개로 늘어나 비용 안전장치가 무의미해지는 것을 막기 위해서다 (운영자 결정, 2026-10-20). 따라서 `has_premium_access_for`가 아니라 실제 구매 여부(`user_pass`)로 판단한다.

### 3.2 서버가 막는다 (내 결정)
- 레시피 생성 Edge Function `create-recipe-by-gemini`에서 생성 전에 한도를 차감하고, 넘으면 생성하지 않는다. 앱 판단은 표시용이다.
- `recipe` 테이블은 저장 안 된 레시피를 30일 뒤 지우므로 횟수 계산에 쓰지 않는다. 사용량을 별도로 기록한다.

### 3.3 보상형 광고는 서버 검증 (내 결정)
- Google AdMob 보상형 광고 + **서버 측 검증(SSV)**. AdMob이 우리 Edge Function을 직접 호출해 "이 유저가 광고를 끝까지 봤다"를 알려줄 때만 보너스를 준다. 앱이 보내는 "봤어요"는 믿지 않는다 (안티 목표 3).
- 앱 라이브러리: `react-native-google-mobile-ads` (Expo 53 호환 버전). 네이티브 모듈이므로 결제와 같은 새 스토어 빌드(6.0.0)에 포함한다.

## 4. 동작

### 4.1 데이터 (초안, 세부는 빌더 재량)
- `quota_setting` (행 1개): `free_daily = 5`, `pass_daily = 20`, `ad_bonus_daily = 3`
- `recipe_usage`: `(uid, day KST)` 기본키, `used`, `ad_bonus` (오늘 받은 광고 보너스 수)
- `ad_reward`: `transaction_id` (unique), `uid`, `created_at`, `raw` — SSV 중복 방지 및 기록
- DB 함수 (service role 전용, `security definer`, 유저 행 잠금으로 동시성 안전):
  - `consume_recipe_quota(uid) → {allowed, remaining, limit, canWatchAd}`: 한도 = (패스면 pass_daily, 아니면 free_daily + ad_bonus). 남아 있으면 `used += 1`.
  - `release_recipe_quota(uid)`: 생성 실패 시 `used -= 1` (0 미만 금지) (안티 목표 1)
  - `grant_ad_bonus(uid, transaction_id, raw) → granted|duplicate|limit`: 같은 transaction_id는 한 번만, 하루 `ad_bonus_daily`까지
- 유저 조회용: `get_recipe_quota()` (auth.uid() 기준) → `{used, limit, remaining, adBonusLeft, isPass}`

### 4.2 레시피 생성 흐름 (`create-recipe-by-gemini`)
1. 유저 확인 (기존과 동일)
2. `consume_recipe_quota` → 막히면 HTTP 429 `{ code: 'QUOTA_EXCEEDED', remaining: 0, canWatchAd }`
3. 레시피·이미지 생성 (기존과 동일)
4. 생성이 실패하면(텍스트/이미지/저장 단계 예외) `release_recipe_quota` 후 기존 오류 응답
- 사용자가 생성 중 취소(앱 AbortController)해도 서버가 이미 생성을 끝냈다면 차감은 유지된다 (비용이 이미 발생). 빌더 재량으로 문서화.

### 4.3 보상형 광고 흐름
1. 앱이 429 `QUOTA_EXCEEDED`를 받으면 안내 모달:
   - "오늘 레시피를 모두 만들었어요. 내일 다시 만들 수 있어요."
   - 무료 유저: `canWatchAd`면 **[광고 보고 1개 더 만들기]**, 판매 중이면 **[패스 보기]** (구독 전용 기능 + 하루 20개 안내)
   - 패스 구매자(20개 소진): 버튼 없이 "오늘 레시피를 모두 만들었어요. 내일 다시 만들 수 있어요."만 (내 결정)
2. [광고 보기] → 보상형 광고 로드·표시. 요청에 SSV `userId = Supabase uid`를 넣는다.
3. 광고 완료 → AdMob이 Edge Function `admob-ssv`(verify_jwt = false)를 호출 → 서명 검증 → `grant_ad_bonus`
4. 앱은 광고 완료 후 `get_recipe_quota`를 짧게 몇 번 조회해 보너스 반영을 확인한 뒤 자동으로 레시피 생성을 다시 시도한다. 일정 시간(예: 10초) 안에 반영 안 되면 "보상 확인이 늦어지고 있어요, 잠시 후 다시 시도해주세요" (안티 목표 2: 보상은 서버에 남아 있으므로 나중에 생성 가능)
- SSV 서명 검증: Google 공개키(`https://www.gstatic.com/admob/reward/verifier-keys.json`, 캐시)로 쿼리 문자열의 ECDSA 서명 검증. `key_id`, `signature`는 쿼리 끝에 있음. 검증 실패·키 미일치는 거절.

### 4.4 표시
- 레시피 제작 화면 버튼 근처에 "오늘 N개 남았어요" (무료 유저). 패스 유저는 남은 수가 5개 이하일 때만 표시 (내 결정).
- 광고는 패스 유저에게 절대 보이지 않음 (안티 목표 4).
- 오프라인이면 기존처럼 네트워크 토스트.

## 5. 운영자 준비 사항
1. AdMob 계정 생성 (admob.google.com, Google 계정으로 가입, 지급 정보는 수익 발생 후 입력 가능)
2. 앱 추가: Android, "Google Play에 게시됨" → 스위치온 레시피 검색해 연결
3. 광고 단위 만들기: **보상형**, 보상 수량 1, 항목 "레시피"
4. 광고 단위의 **서버 측 검증(SSV)** 콜백 URL에 `admob-ssv` 함수 주소 입력
5. 앱 ID, 광고 단위 ID 전달 (공개 값이라 앱에 들어가도 됨)
6. `app-ads.txt`는 개발자 웹사이트가 있을 때 권장 (없으면 생략 가능, 빌더가 안내)
- 개발 중에는 Google 테스트 광고 단위 ID를 사용한다 (실제 광고 클릭으로 계정 정지되는 것 방지).

## 5.1 개발용 테스트 함수

- 개발용 앱(`__DEV__`)은 `create-recipe-by-gemini-test`를 부른다 (`api/gemini.ts`). 이 함수는 저장소에 없던 실서버 전용 사본이었고, Google에서 제거한 Imagen 4를 아직 호출하고 있었다 (2026-10-20 확인, 개발용 앱의 이미지 생성이 실패하는 상태).
- 레시피 생성 로직을 공용 모듈로 옮기고, 두 함수가 같은 코드를 쓰게 한다. 한도 기능도 두 함수에 똑같이 적용된다 (운영자 결정: 추천안 승인, 2026-10-20).

## 6. 출시 순서
1. DB 마이그레이션 + `admob-ssv` 배포 + `create-recipe-by-gemini` 수정 배포
   - 이 시점부터 구버전 앱도 한도가 적용된다. 패스 무료 기간 시작과는 무관하게 동작한다 (위 3.1). 구버전 앱은 429를 이해하지 못하므로, 서버 응답 문구가 기존 오류 토스트로 보일 수 있다 → 구버전에도 의미가 통하는 오류 메시지를 함께 보낸다 (빌더 재량). 무료 5개라 현재 유저는 거의 걸리지 않는다.
2. 앱(모달, 남은 수, 광고)은 결제와 함께 6.0.0 스토어 빌드로 출시

## 7. 검증
- DB 함수: 무료/패스/광고 보너스 한도, KST 자정 경계, 동시 요청 2개가 한도 1을 넘지 않음, 실패 시 release, transaction_id 중복, 보너스 하루 3회 제한
- SSV 서명 검증: Google 문서의 테스트 벡터 또는 직접 만든 키로 단위 테스트, 변조된 쿼리 거절
- 앱: 429 처리 모달, 광고 완료 후 재시도, 패스 유저 광고 미노출, 오프라인

## 8. 빌더 재량
테이블·함수 이름, 429 응답 세부, 광고 완료 후 확인 주기, 남은 수 표시 위치·문구, 라이브러리 버전.
