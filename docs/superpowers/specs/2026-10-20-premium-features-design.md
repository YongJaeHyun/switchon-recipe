# 구독 전용 기능 3종 설계 (편의점 판정 · 맞춤 레시피 추천 · 체중 기록 + AI 주간 리포트)

- 작성일: 2026-10-20
- 상태: 초안 (승인 대기, 빌더 검토 반영)
- 관련: 스위치온 패스 (`docs/superpowers/specs/2026-10-19-switchon-pass-payment-design.md`). 세 기능은 패스의 "구독 전용 기능 판단 장치"(`has_premium_access_for`, `_shared/premium.ts`) 위에서 동작한다. 레시피 한도 (`docs/superpowers/specs/2026-10-20-recipe-quota-rewarded-ad-design.md`).

## 1. 배경과 목적

스위치온 패스(5주 이용권)를 팔려면 "패스를 사면 이런 걸 할 수 있다"를 보여줄 기능이 필요하다. 처음 후보(냉장고 사진, 주간 식단표)는 운영자 검토에서 빠졌고, 다음 세 기능으로 정했다.

| 기능 | 유저가 얻는 것 |
|---|---|
| 편의점 판정 | 밖에서 "이거 지금 먹어도 돼?"를 바로 안다 |
| 맞춤 레시피 추천 | 오늘 뭐 먹을지 고민을 덜어준다 |
| 체중 기록 + AI 주간 리포트 | "나 잘하고 있나?"를 숫자로 확인하고 다음 주를 준비한다 |

세 기능이 각각 "밖에서 먹을 때 / 집에서 만들 때 / 진행 상황"을 맡아 겹치지 않는다. 홍보할 때 세 가지 다른 가치로 보여줄 수 있다.

## 2. 출시 조건 (운영자 결정)

- **세 기능이 모두 완성된 뒤에** 무료 기간과 패스 판매를 함께 연다. 홍보 문구에 세 기능을 모두 넣기 위해서다.
- 기능 코드는 OTA로 내보낸다. 필요한 네이티브 모듈(`expo-image-picker`)은 6.0.0 스토어 빌드에 미리 들어간다. 6.0.0이 깔린 유저만 받는다.
- 무료 기간 시작일 설정(`premium_setting`)은 운영자가 세 기능 OTA 배포 다음 날로 한다. 그 전에는 판매하지 않는다 (패스 설계 그대로).

## 3. 공통 규칙

- **이용 조건**: 서버(Edge Function)가 `has_premium_access_for(uid)`로 판단한다. 무료 기간에는 모두 쓸 수 있고, 무료 기간이 끝나면 패스 보유자만 쓴다. 앱 판단은 표시용이다.
- **잠긴 상태 표시**: 무료 기간이 아니고 패스도 없으면 기능 입구는 그대로 보이되, 누르면 기능 소개 + [패스 보기] 화면을 띄운다. 판매하지 않는 시기(무료 기간 시작 전, 결제 불가 빌드)에는 입구를 아예 숨긴다.
- **하루 사용 한도**: AI 비용이 드는 동작은 레시피 한도와 같은 방식(`quota_setting` 계열 설정 + 유저·날짜별 사용량, 서버에서 차감, 실패 시 되돌림)으로 막는다. 값은 DB 설정으로 바꿀 수 있다.
- **이용 조건이 끝난 뒤 (운영자 결정)**: 무료 기간이 끝나거나 패스가 만료돼도 이미 받은 주간 리포트와 판정 기록은 계속 볼 수 있다. 새 판정, 새 리포트 생성, 맞춤 추천만 막는다. 기록 읽기는 RLS(본인 행)로 직접 읽고 이용 조건을 확인하지 않는다.
- **오프라인**: 기존처럼 네트워크 토스트만 띄운다.
- **AI 모델**: 판정·태깅·리포트는 텍스트/비전이 되는 Gemini Flash 계열을 쓴다 (빌더 재량, 현재 재료 판정에 쓰는 `gemini-2.5-flash` 기준).
- **건강 문구**: 의료 조언처럼 들리는 표현을 쓰지 않는다. 스위치온 가이드 범위 안에서만 말한다.

## 4. 기능 A: 편의점 판정

### 4.1 쓰는 순간
편의점 진열대 앞에서 "이거 지금 먹어도 되나?"를 바로 알고 싶을 때 (운영자 답변).

### 4.2 입력 (운영자 결정)
세 가지 중 하나로 한 번에 하나를 판정한다.
1. **제품 앞면 사진** 한 장: AI가 제품을 알아보고 일반적인 성분으로 추정한다.
2. **성분표·영양성분표 사진** 한 장: 적힌 당류·탄수화물·원재료를 읽어 판정한다. 더 정확하다.
3. **글자 입력**: "참치마요 삼각김밥" 같은 제품명·음식 이름. 추정으로 판정한다.

사진은 카메라 촬영과 앨범 선택 모두 가능 (`expo-image-picker`). 업로드 전 긴 변 1280px 정도로 줄인다 (빌더 재량).

### 4.3 결과
- **점수 1~10점**과 한 줄 결론. 5점 이상은 "괜찮아요"(느슨하게 허용), 4점 이하는 "피하세요" 쪽으로 표시한다 (운영자 결정, 이전 대화).
- 기준은 **유저의 현재 주차**다. 같은 제품도 주차에 따라 점수가 달라질 수 있다. 유지기(5주차+)는 4주차 기준에 "정제 탄수화물·당 주의"를 더한다 (내 결정).
- **이유** 1~2줄 (예: "당이 많은 소스가 들어 있어요").
- **근거 표시**: 앞면 사진·글자 입력이면 "추정", 성분표 사진이면 "성분표 기준"을 작게 표시한다. 추정 결과에는 [성분표 찍고 더 정확히 보기] 버튼을 둔다.
- **점수가 낮으면 대체 제품** 2~3개를 추천한다 (운영자 결정). 실제 매장 재고는 알 수 없으므로 흔한 편의점 상품(삶은 달걀, 닭가슴살, 무가당 두유 등) 위주로, 현재 주차에 맞는 것만.
- 제품을 알아볼 수 없으면 점수를 내지 않고 "제품명이 잘 보이게 다시 찍어주세요"를 보여준다. 이 경우 사용 횟수는 되돌린다.

### 4.4 판정 기록 (운영자 결정)
- 판정마다 기록을 남긴다: 입력 종류, 사진 썸네일 또는 입력 글자, 인식한 제품명, 점수, 결론, 이유, 대체 추천, 주차, 시각.
- 판정 화면에서 최근 기록 목록을 보고 다시 열 수 있다. 사진 원본은 Storage에 두고 30일 뒤 지운다 (내 결정, 비용·개인정보). 목록용 작은 썸네일(약 200px)은 따로 저장해 계속 남기고, 텍스트 기록도 남긴다.

### 4.5 하루 사용 한도 (운영자 결정, 숫자는 내 결정)
- 하루 30회 (KST 자정 기준). DB 설정으로 변경 가능.
- 다 쓰면 "오늘 판정을 모두 사용했어요 · 자정에 다시 채워져요". 광고 보상은 없다 (패스 기능이므로).

## 5. 기능 B: 맞춤 레시피 추천

### 5.1 쓰는 순간
"오늘 뭐 먹지?" 고민을 덜고 싶을 때. 지금 먹고 싶은 것과 상황을 고르면 현재 주차에 맞는 레시피를 추천받는다.

### 5.2 조건 (운영자 승인)
| 조건 | 선택지 |
|---|---|
| 맛 | 매운 것 / 안 매운 것 / 상관없음 |
| 종류 | 한식 / 양식 / 중식 / 일식 / 상관없음 |
| 요리 방식 | 볶음 / 구이 / 국·탕 / 찜 / 샐러드 / 덮밥 / 상관없음 |
| 조리 시간 | 15분 이내 / 30분 이내 / 상관없음 |
| 끼니 | 아침 / 점심 / 저녁 (주차별 끼니 규칙으로 저탄수·무탄수 자동 결정) |
| 꼭 넣을 재료 | 등록 재료 중 1~2개 (선택) |
| 빼고 싶은 재료 | 등록 재료 여러 개 (선택, 저장되어 다음에도 적용) |

모든 조건은 선택이다. 아무것도 안 골라도 현재 주차·끼니 기준으로 추천한다.

### 5.3 결과 (운영자 결정: 기존 레시피 먼저, 없으면 새로 만들기)
1. 기존 레시피(`recipe` 테이블, 현재 약 600개) 중 조건에 맞는 것을 3~5개 카드로 보여준다. 현재 주차보다 늦은 주차 레시피는 제외하고, 빼고 싶은 재료가 들어간 레시피는 제외한다. 꼭 넣을 재료가 있으면 포함한 것만. 같은 조건으로 다시 누르면 다른 레시피가 나오도록 섞는다.
2. 카드 아래 **[이 조건으로 새로 만들기]**: 기존 레시피 생성 흐름(`create-recipe-by-gemini`)에 조건을 넘겨 새로 만든다. **하루 레시피 한도에 포함**된다 (한도 초과 시 기존 모달).
3. 맞는 기존 레시피가 하나도 없으면 바로 "새로 만들기"를 크게 보여준다.

기존 레시피 추천 자체는 AI 호출이 없으므로 하루 한도를 두지 않는다 (내 결정).

- **서버 판단 (내 결정)**: 추천 조회는 이용 조건을 확인하는 RPC/Edge Function을 거친다 (`has_premium_access_for`). 클라이언트가 레시피 뷰를 직접 걸러 쓰는 방식은 쓰지 않는다. 필터·섞기·제외 재료 처리도 이 서버 함수에서 한다.
- **새로 만들기의 조건 전달 (내 결정)**: 맛·조리 시간·꼭 넣을 재료 등 조건을 `create-recipe-by-gemini`에 넘기는 것은 패스 여부와 상관없이 허용한다. 무료 유저도 레시피 제작 화면에서 이미 종류·방식을 고를 수 있고, 생성 자체는 하루 레시피 한도로 막히기 때문이다. 패스 전용은 "추천 화면"이다.
- **끼니와 저탄수·무탄수 (내 결정)**: 끼니 규칙은 `BASE_TODOS`(주차·일차별 할 일)를 따른다. 그 끼니가 쉐이크인 주차·일차에는 해당 끼니 선택지를 비활성화하고 "이 끼니는 프로틴쉐이크예요"를 보여준다. 1주차처럼 모든 끼니가 쉐이크면 추천 화면 입구에 "2주차부터 쓸 수 있어요"를 표시한다. 끼니 자체는 태그가 아니라 저탄수/무탄수(`is_zero_carb`)와 주차로 걸러진다.

### 5.4 레시피 태그 (내 결정)
- 기존 레시피에는 "매운지, 종류, 요리 방식, 끼니 적합" 정보가 없다. 태그 컬럼(예: `spicy`, `cuisine`, `method`)을 추가하고, 기존 레시피는 AI로 한 번 일괄 태깅한다 (텍스트만, 전체 몇백 원 수준).
- 새로 생성되는 레시피는 생성 시 같은 태그를 함께 만든다 (`createRecipe.ts`의 응답 스키마 확장).
- 조리 시간은 기존 `cooking_time`, 재료는 기존 `ingredients`를 쓴다.
- 공개 범위: 추천 대상은 탐색 탭에 이미 공개되는 레시피와 같은 범위로 한다 (빌더가 탐색 탭 쿼리 기준을 확인해 맞춘다).

## 6. 기능 C: 체중 기록 + AI 주간 리포트

### 6.1 쓰는 순간
"나 잘하고 있나?"를 확인하고 싶을 때. 스위치온은 4주 프로그램이라 진행 상황 확인이 꾸준히 쓰게 하는 가장 큰 동기다.

### 6.2 체중 기록 (무료, 운영자 결정)
- 홈에서 한 번 눌러 오늘 체중 입력. kg, 소수점 한 자리. 어제 값이 미리 채워진다.
- 하루 1개 (KST 날짜 기준). 다시 입력하면 그날 값을 바꾼다. 지난 날짜 수정·삭제 가능.
- **그래프**: 시작일부터의 변화를 주차별 색(기존 `getWeekColorHex`)으로 표시. 시작 체중 대비 변화량도 함께.
- **알림 (내 결정)**: 기본은 꺼져 있다. 처음 체중을 입력하면 "매일 아침 기록 알림 받을래요?"를 한 번 묻고, 켠 유저에게만 입력 안 한 날 오전 9시(KST)에 푸시한다. 설정은 서버에 저장한다(cron이 대상을 고르므로). 기존 푸시 함수는 문의(`INQUIRY`)만 처리하므로 새 알림 종류를 추가한다.
- **시작일 변경 (내 결정)**: 모든 기록(체중·할 일·단식·판정)은 **날짜**로 저장하고 주차는 조회 시 현재 `start_date`로 계산한다. 시작일을 바꾸면 그래프는 새 시작일부터 보여주되 [전체 기간 보기]로 이전 기록도 볼 수 있다. 이미 만든 주간 리포트는 지우지 않고, 만들 당시의 시작일과 주차를 함께 저장해 "이전 프로그램" 리포트로 구분해 보여준다 (`weekly_report`의 키는 `(uid, start_date, week_index)`).
- 헬스 커넥트 등 외부 연동은 하지 않는다 (운영자 결정: Play 건강 데이터 심사 부담, 이후 요청 많으면 별도 빌드로).

### 6.3 리포트에 필요한 새 기록 (내 결정)
지금은 하루 할 일 완료율만 남고(`statistics.todo_rate`), 어떤 할 일을 체크했는지와 단식 성공 여부는 남지 않는다. 구체적인 리포트를 위해 다음을 새로 기록한다 (6.0.0 이후부터 쌓임):
- **할 일 일별 기록**: 날짜별로 그날 할 일 목록과 체크한 항목. 하루가 끝날 때 또는 체크할 때마다 저장 (빌더 재량).
- **단식 결과**: 단식 요일마다 성공/중단/기록 없음. 기존 단식 카드(`FastingCard`)의 "단식 완료" 시점에 [성공했어요] / [중간에 먹었어요] 버튼을 두어 기록한다. 응답이 없으면 "기록 없음".
  - 기록 날짜는 **단식을 시작한 날** (내 결정). 단식 중에도 [중간에 먹었어요]를 누를 수 있고, 끝난 뒤에는 다음 단식 시작 전 또는 48시간 안에 답할 수 있다.
  - 리포트의 "계획 N회"는 그 주에 유저가 정해둔 단식 요일 수(그 주 기준 저장값)다. 주 중간에 요일을 바꾸면 바뀐 뒤 요일로 센다.

### 6.4 AI 주간 리포트 (패스 전용, 운영자 결정)
- **언제**: 유저의 주차가 바뀌는 날 아침(KST 8시, 내 결정)에 지난 주차 리포트를 만든다. 서버 cron이 대상 유저(이용 조건 충족 + 그 주에 기록이 1개 이상)를 찾아 생성하고 푸시로 알린다. 유지기(5주차+)도 매주 만든다.
- **무료 유저**: 리포트는 만들지 않는다 (비용). 대신 "이번 주 리포트를 받아보세요 · 패스 보기" 미리보기 카드를 보여준다 (판매 중일 때만).

**리포트 내용 (운영자 요청: 구체적으로)** — 숫자와 날짜를 근거로 쓰고, 막연한 칭찬·격려만으로 채우지 않는다. 고정 구성:

1. **한 줄 요약**: 예 "단식 2번 모두 성공, 1.2kg 감량. 저녁 무탄수식은 이번 주 가장 약했어요."
2. **숫자로 본 이번 주** (AI가 아니라 서버가 계산해 그대로 표시)
   - 체중: 주 시작 → 주 끝, 변화량, 기록한 날 수, 시작일 대비 누적 변화
   - 할 일 완료율: 주 평균, 가장 높은 날·낮은 날 (요일과 %)
   - 할 일별 달성: 항목별 "나온 날 중 N일" (예: 아침 쉐이크 7/7, 저녁 무탄수식 3/5). 분모는 그 할 일이 실제로 목록에 있었던 날 수다 (단식일·1주차 3일 이후 등 날마다 목록이 다르므로, 내 결정)
   - 단식: 계획 N회 중 성공 N회, 중단 N회 (요일 표시)
   - 만든 레시피: N개 (저탄수 N, 무탄수 N), 편의점 판정 N회 중 "피하세요" N회
3. **잘한 점 1개**: 위 숫자 중 하나를 근거로 (예: "아침 쉐이크를 7일 모두 지켰어요").
4. **아쉬운 점 1개 + 구체적 행동 1개**: 가장 낮은 항목을 근거로, 다음 주에 할 수 있는 행동 하나 (예: "저녁 무탄수식을 3번 놓쳤어요. 저녁 메뉴를 미리 정해두면 좋아요 → [무탄수 저녁 추천 보기]" 버튼은 맞춤 레시피 추천으로 연결, 조건 미리 채움).
5. **체중 해석**: 변화가 크거나 늘었을 때 탓하지 않고 설명 (예: "주 초반 체중은 수분 영향이 커요. 단식 다음 날 측정값은 낮게 나오는 편이에요"). 기록이 2일 미만이면 이 칸은 "체중을 2일 이상 기록하면 변화를 분석해드려요".
6. **다음 주에 달라지는 점**: 다음 주차 규칙 변화 (기존 `WEEK_CHANGES` 내용 기반)와 이번 주 기록을 연결 (예: "다음 주부터 단식이 3회로 늘어요. 이번 주 단식은 목·일에 성공했으니 같은 요일을 유지해보세요").

- 2번은 서버가 계산한 숫자를 그대로 쓰고, AI는 1·3·4·5·6의 문장만 만든다. AI가 숫자를 지어내지 않도록 프롬프트에 계산된 값만 넣고, 응답에 없는 숫자가 나오면 버린다 (빌더 재량으로 검증 방식 결정).
- 기록이 거의 없는 주(체중 0일 + 할 일 체크 0일)는 리포트 대신 "이번 주는 기록이 없어요" 카드만.
- **지난 리포트**: 프로필 "나의 4주 리포트" 옆 [주간 리포트]에서 주차별로 다시 본다.

## 7. 데이터 (초안, 세부는 빌더 재량)
- `premium_usage` 또는 기능별 사용량: `(uid, day, feature)` 기본키, `used` — 편의점 판정 한도
- `food_check`: 판정 기록 (uid, input_type, image_path, input_text, product_name, score, verdict, reasons, alternatives, week, basis(추정/성분표), created_at)
- `recipe` 태그 컬럼 추가 + `user_recipe_preference` (빼고 싶은 재료)
- `weight_log`: (uid, day) 기본키, weight_kg numeric(4,1)
- `todo_daily`: (uid, day) 기본키, items(jsonb: 할 일 목록), checked(jsonb)
- `fasting_result`: (uid, day) 기본키, result('success'|'broken')
- `weekly_report`: (uid, week_index) 기본키, stats jsonb, content jsonb, created_at
- RLS: 본인 행만 읽기/쓰기. 사용량·리포트 생성은 service role 함수만.

## 8. 목표 / 비목표 / 안티 목표

### 목표
- 세 기능이 각각 하나의 화면 흐름으로 완결되고, 패스 이용 조건을 서버에서 지킨다.
- 리포트가 숫자와 날짜를 근거로 구체적이다.

### 비목표
- 냉장고 사진 인식, 주간 식단표·장보기 (운영자가 제외)
- 헬스 커넥트·외부 기기 연동
- iOS
- AI 코치 자유 대화

### 안티 목표
1. 판정·리포트가 의료 조언처럼 들림
2. AI가 숫자(체중, 횟수)를 지어냄
3. 패스가 없는데 서버를 직접 불러 기능을 씀
4. 체중이 늘었을 때 유저를 탓하는 말투
5. 기능이 실패했는데 사용 횟수만 줄어듦

## 9. 검증
- 서버: 이용 조건(무료 기간/패스/없음), 하루 한도와 실패 시 되돌림, 리포트 숫자 계산(주 경계 KST, 기록 누락 날), 판정 응답 파싱 실패 처리
- 판정: 앞면·성분표·글자 각각 실제 예시 몇 개로 점수 경향 확인 (주차별로 다른지)
- 추천: 조건 조합별 결과 수, 빼고 싶은 재료 제외, 결과 없을 때 새로 만들기
- 리포트: 기록 많은 주 / 적은 주 / 없는 주 샘플로 문장 품질과 숫자 일치 확인
- 앱: 잠금 화면, 판매 안 할 때 입구 숨김, 오프라인

## 10. 빌더 재량
화면 배치와 진입 위치(홈 카드/탭), 테이블·함수 이름, 프롬프트 문구, 사진 축소 크기, 리포트 cron 구현 방식, 할 일 일별 기록 저장 시점, 태그 값 목록 세부.

## 11. 내가 정한 것 (운영자 확인용)
- 판정 하루 30회, 사진 원본 30일 보관, 제품 인식 실패 시 횟수 되돌림
- 유지기 판정 기준 = 4주차 + 당 주의
- 기존 레시피 추천은 횟수 제한 없음, 새로 만들기는 레시피 한도 포함
- 레시피 AI 태깅 (기존 일괄 + 신규 생성 시)
- 체중 알림 오전 9시, 리포트 생성 주차 바뀌는 날 오전 8시
- 단식 성공/중단을 단식 카드에서 직접 기록
- 리포트 "숫자로 본 이번 주"는 서버 계산값, AI는 문장만
- 무료 유저는 리포트 미생성 + 미리보기 카드
