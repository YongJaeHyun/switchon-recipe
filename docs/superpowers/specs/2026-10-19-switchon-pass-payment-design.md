# 스위치온 패스 (결제·구독 전용 기능 잠금) 설계

- 작성일: 2026-10-19
- 상태: 초안 (승인 대기)
- 관련: 이후 만들 구독 전용 기능 3개(외식·편의점 판정, 냉장고 사진 재료 선택, 주간 식단표·장보기)가 이 결제 기능 위에서 동작한다. 기능 자체는 각각 별도 설계.

## 1. 배경과 목적

운영자는 앱을 유료로도 운영하려 한다. 스위치온 다이어트는 길어야 5주 정도라 유지기에 들어가면 앱을 쓸 이유가 줄어든다. 그래서 매달 자동 결제를 붙드는 구독보다, **다이어트 기간에 한 번 결제하는 기간 이용권**이 맞다는 데 합의했다.

**목표 상태:** 구독 전용 기능을 배포한 다음 날부터 2주 동안은 모든 유저가 무료로 쓴다. 이 기간에 "스위치온 패스"를 사면 크게 할인받는다. 무료 기간이 끝나면 패스가 있는 유저만 구독 전용 기능을 쓴다.

## 2. 목표 / 비목표 / 안티 목표

### 목표
- 5주 이용권 "스위치온 패스" 판매 (Google Play 인앱결제)
- 무료 기간(배포 다음 날부터 2주) 동안 모든 유저에게 구독 전용 기능 개방
- 무료 기간 중 사전 결제 할인: 무료 기간이 많이 남았을수록 더 싸게
- 서버가 "이 유저가 지금 구독 전용 기능을 쓸 수 있는가"를 판단 (앱 조작으로 우회 불가)
- 기기를 바꾸거나 앱을 지웠다 다시 깔아도, 같은 계정이면 패스가 유지됨

### 비목표
- 자동 갱신 구독
- iOS (앱이 안드로이드 전용)
- "다음 도전 할인", 친구 초대 할인 (이후에 별도로)
- 구독 전용 기능 3개 자체의 구현 (각각 별도 설계)
- 기존 무료 기능(레시피 생성, 재료 요청, 주차 가이드 등) 잠금

### 안티 목표
1. 돈을 냈는데 기능이 잠겨 있음 (결제 검증 실패, 기기 변경, 네트워크 문제 등)
2. 돈을 안 냈는데 앱을 조작해서 기능을 쓸 수 있음
3. 무료 기간에 일찍 산 유저가 늦게 산 유저보다 손해 봄
4. 기존 무료 기능이 갑자기 막힘

## 3. 결정된 내용

### 3.1 상품과 가격 (운영자 결정)

| 언제 사는지 | 가격 | 할인율 |
|---|---|---|
| 무료 기간 1주차 (무료 기간 1~7일째) | 1,900원 | 약 61% |
| 무료 기간 2주차 (무료 기간 8~14일째) | 2,900원 | 약 40% |
| 무료 기간 이후 | 4,900원 | 정가 |

- 패스는 **산 순간부터 5주(35일)** 동안 유효하다. 운영자가 무료 기간이 끝난 뒤로 시작을 미루는 방안을 검토했다가 택하지 않았다. 다이어트가 보통 5주면 끝나서, 미루면 다이어트 기간을 넘겨버리기 때문이다. 일찍 산 유저는 대신 더 큰 할인을 받는다.
- 날짜 기준은 한국 시간(KST)이다.
- 패스가 남아 있을 때 다시 사면, **남은 기간 끝에서부터** 5주가 이어서 붙는다. (내 결정. 손해 보는 사람이 없도록)

### 3.2 결제 방식 (내 결정)

- **Google Play 일회성 상품(소모성) 3개**로 판다. 상품 ID는 예를 들어 `switchon_pass_5w_1900`, `switchon_pass_5w_2900`, `switchon_pass_5w_4900`.
- 만료일은 우리 서버가 계산한다: `max(현재 패스 만료일, 구매 시각) + 35일`.
- 이렇게 정한 이유:
  - Google Play 선불 요금제는 기간을 정해진 단위(주/월 등)로만 고를 수 있어 5주를 만들 수 없다. 선불 요금제에는 할인 오퍼도 붙일 수 없다.
  - 자동 갱신이 없으니 RevenueCat 같은 구독 관리 서비스가 줄 이점이 적다. RevenueCat은 선불 요금제 지원도 불완전하다.
  - 일회성 상품은 기간과 가격 구간을 우리가 자유롭게 정할 수 있다.
- 앱 쪽 결제 라이브러리는 Expo 53과 호환되는 것을 쓴다 (예: `react-native-iap` 또는 `expo-iap`). 선택은 빌더 재량이다. 네이티브 모듈이 추가되므로 **새 앱 빌드(스토어 배포)가 필요하다**.

### 3.3 무료 기간 설정 (운영자 결정 + 내 결정)

- 무료 기간은 "기능을 배포한 다음 날부터 2주"다 (운영자 결정).
- 시작일과 종료일은 앱 코드가 아니라 **DB 설정**에 둔다. 앱 업데이트 없이 바꿀 수 있게 하기 위해서다 (내 결정).
- 가격 구간(1주차/2주차/정가)도 이 설정으로 계산한다.
- **무료 기간은 구독 전용 기능 전체에 하나**다. 첫 번째 구독 전용 기능(외식·편의점 판정)이 배포될 때 결제 기능도 함께 배포하고, 운영자가 그 다음 날을 시작일로 설정한다. 이후 기능은 무료 기간과 상관없이 추가된다 (내 결정).
- **판매 스위치**: 무료 기간 설정이 비어 있으면 아무 상품도 팔지 않고 결제 화면도 숨긴다. 구독 전용 기능이 하나도 없을 때 패스가 팔리는 일을 막기 위해서다 (내 결정).
- **무료 기간 시작 전**(설정은 됐지만 시작일 전): 구독 전용 기능은 잠겨 있고, **판매하지 않는다**(결제 화면 숨김). 무료 기간 첫날부터 1,900원으로 판매를 시작한다. 하루 먼저 산 사람이 정가를 내는 일을 막기 위해서다 (운영자 결정, 2026-10-20). 이미 정가 상품을 결제한 경우(조작된 앱 등)는 환불하지 않고 패스를 준다 (내 결정).

### 3.4 잠금 대상

- 구독 전용 기능 3개만 잠근다. 기존 기능은 전부 무료로 유지한다.
- 이 설계에서는 "구독 전용 기능을 쓸 수 있는가"를 판단하는 공통 장치만 만든다. 각 기능은 이 장치를 호출해 쓴다.

## 4. 동작

### 4.1 이용 가능 여부 (`premium access`)

유저가 구독 전용 기능을 쓸 수 있는 조건:
- 지금이 무료 기간 안이거나,
- 유효한 패스가 있다 (`pass_expires_at > 지금`).

- **서버가 최종 판단한다.** 구독 전용 기능은 Edge Function을 거치게 될 것이므로, 각 함수가 같은 판단 함수를 호출해 막는다.
- 앱도 같은 정보를 받아 화면 표시(잠금 아이콘, 결제 화면 이동)에 쓴다. 앱 판단은 표시용일 뿐이다.

### 4.2 구매 흐름

1. 앱이 서버에서 "지금 팔 상품 ID"를 받는다. 무료 기간 날짜로 계산하며, 서버 기준 시각을 쓴다.
2. 유저가 결제 화면에서 구매한다 (Google Play 결제창).
3. 앱이 구매 토큰을 Edge Function(예: `verify-pass-purchase`)으로 보낸다.
4. Edge Function은 다음 순서로 처리한다.
   - Google Play Developer API로 구매를 검증한다 (상태, 상품 ID, 패키지명).
   - 같은 구매 토큰이 이미 처리됐는지 확인한다. 중복이면 기존 결과를 그대로 반환한다.
   - 만료일을 갱신한다.
   - 구매를 **소비(consume)** 처리해서 다시 살 수 있게 만든다.
5. 앱은 서버 응답을 받은 뒤에 "패스 활성화" 화면을 보여준다.

**구매 가격 구간 검증:** 앱이 보여준 상품과 서버가 계산한 구간이 다를 수 있다 (예: 2주차 마지막 날 밤 11시 59분에 결제). 구간이 끝난 뒤 **유예 시간 안**의 구매는 유저에게 불리하게 처리하지 않고 5주를 준다. 유예 시간은 **구간이 끝난 뒤 하루(24시간)**다. 그 이후에 지난 구간의 싼 상품을 산 경우(오래되거나 조작된 앱)는 **Google Play API로 자동 환불하고 패스를 주지 않는다**. 앱에는 "가격이 바뀌어 결제가 취소됐어요"를 보여준다 (운영자 결정, 2026-10-19).

### 4.3 결제 누락 복구 (안티 목표 1)

- 결제는 됐는데 서버 검증 전에 앱이 꺼지거나 네트워크가 끊길 수 있다. 이 경우 앱을 다시 열면 **처리 안 된 구매를 다시 서버로 보낸다** (결제 라이브러리의 미완료 구매 조회 사용).
- Google Play는 3일 안에 확인(acknowledge)이나 소비가 안 된 구매를 자동 환불한다. 검증과 소비는 반드시 서버에서 끝낸다.
- 다른 기기에서 로그인해도 패스는 계정(Supabase uid)에 묶여 있으므로 그대로 유지된다.

### 4.4 환불

- 유저가 Google Play에서 환불받으면 해당 패스 기간을 회수한다.
- Google Play의 **환불된 구매 조회 API(Voided Purchases API)**를 하루 한 번 확인한다 (Supabase cron). 빌더는 실시간 알림(RTDN)을 써도 된다.
- 회수 방식: 환불된 구매를 `voided`로 바꾼 뒤, **남은 `granted` 구매들로 만료일을 처음부터 다시 계산**한다. 구매 시각 순서로 `max(이전 만료일, 구매 시각) + 35일`을 반복한다. 겹친 패스나 이미 다 쓴 패스가 환불돼도 결과가 일관된다 (내 결정).
- 같은 계산 함수를 구매 처리에도 쓴다. 그래서 `granted_from`/`granted_until`은 기록용이고, 만료일의 기준은 재계산 결과다.

### 4.5 결제 화면과 진입점 (내 결정, 세부는 빌더 재량)

- **결제 화면(페이월):**
  - 패스 설명 (5주, 구독 전용 기능 3개 소개)
  - 현재 가격
  - 할인 중이면 정가 취소선과 "무료 기간 N일 남음"
  - 다음 구간 가격 예고 (예: "다음 주부터 2,900원")
- **진입점:**
  - 무료 기간 중: 홈 화면에 사전 결제 할인 배너
  - 무료 기간 후: 잠긴 기능을 누르면 결제 화면으로 이동
  - 프로필 화면: 패스 상태 (남은 기간, 만료일)
- **문구 원칙:** "구독" 대신 "패스", "자동 결제 없음"을 분명히 쓴다.

### 4.6 데이터 (초안, 세부는 빌더 재량)

- `app_setting` (또는 기존 설정 테이블): `premium_free_start`, `premium_free_end` (KST 날짜)
- `pass_purchase`:
  - `id`, `uid`, `product_id`, `purchase_token` (unique), `order_id`, `price_krw`
  - `purchased_at`, `granted_from`, `granted_until`
  - `status` (`granted` / `voided`), `raw` (검증 응답)
- `user_pass` (또는 `user` 테이블 컬럼): `uid`, `pass_expires_at`
- RLS:
  - 유저는 본인 패스 상태만 읽는다.
  - 쓰기는 Edge Function(service role)만 한다.
  - 구매 기록은 유저가 읽지 않는다 (내 결정).
- 판단 함수: DB 함수 `has_premium_access(uid)`. Edge Function과 앱 조회가 같은 로직을 쓰게 한다.

### 4.7 회원 탈퇴 (운영자 결정)

- 탈퇴하면 남은 패스 기간도 사라진다. 탈퇴 확인 창에 남은 기간이 있으면 "남은 패스 기간(N일)도 함께 사라져요"라고 경고한다.
- 결제 기록(`pass_purchase`)은 전자상거래법의 거래 기록 보관 의무(5년) 때문에 지우지 않는다. 대신 유저와의 연결을 끊는다 (`uid`를 null로). 주문번호와 금액, 일시는 남긴다.
- 그래서 `pass_purchase.uid`는 `on delete set null`이고, 패스 만료일은 유저와 함께 지워지는 곳에 둔다.

## 5. 운영자 준비 사항 (진행 중)

1. 개인사업자 등록 (722000 응용 소프트웨어 개발 및 공급업, 일반과세자), 통신판매업 신고
2. Play 콘솔 결제 프로필 생성, 계좌 확인
3. 결제 기능이 들어간 빌드를 내부 테스트 트랙에 업로드 (빌더가 만든 뒤, `scripts/`의 빌드 스크립트 사용)
4. 일회성 상품 3개 등록, 라이선스 테스터 등록
5. Google Cloud 서비스 계정 생성 → Play 콘솔에서 권한 부여 → 키를 Supabase 시크릿으로 등록

3~5는 빌더가 단계별로 안내한다.

## 6. 검증

- **단위 테스트:**
  - 가격 구간 계산: 무료 기간 1일째, 7일째, 8일째, 14일째, 15일째, 시작 전. KST 자정 경계 포함
  - 만료일 계산: 첫 구매, 패스가 남았을 때 재구매, 만료 후 재구매
  - `has_premium_access`: 무료 기간 안/밖, 패스 있음/없음/만료
  - 같은 구매 토큰 중복 처리
  - 지난 구간 상품: 유예 24시간 안 → 지급, 밖 → 환불 처리 대상
  - 환불 회수
- **결제 테스트:** 라이선스 테스터 계정으로 실제 결제 흐름을 확인한다.
  - 결제 → 즉시 활성화
  - 결제 직후 앱 강제 종료 → 재실행 시 복구
  - 다른 기기에서 로그인해도 유지
  - 환불 → 회수
  - 탈퇴 → 패스 사라짐, 결제 기록은 uid 없이 남음
- **안티 목표 확인:** 앱에서 API를 직접 호출해도 패스가 생기지 않는다. 가짜 구매 토큰은 서버 검증에서 거절된다.

## 7. 빌더 재량

결제 라이브러리 선택, 테이블·함수 이름, 결제 화면 디자인, 환불 확인 방식(cron vs RTDN), 상품 ID 이름.
